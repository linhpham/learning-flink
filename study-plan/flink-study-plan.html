Module 0 · week 1

Orientation & the local lab

Two goals this week: install the right mental model, and get a real Flink cluster running on your laptop. By the end you'll have submitted a job, read its execution graph in the Web UI, and killed a TaskManager on purpose to watch what happens.

The ideas

Streaming is the general case. Your batch career has trained you to think of data as a finite table that exists, gets scanned, and produces a result. Flink inverts this: data is an unbounded stream of events, and a "table" is just what you get if you stop the stream and look at it. A batch job is simply a streaming job over a stream that happens to end. This is why one engine handles both in Flink, and why the streaming concepts you learn here (time, state, windows) are the primitives and batch is the special case.

The runtime has exactly three moving parts. A JobManager is the coordinator: it accepts jobs, schedules work, and orchestrates recovery. TaskManagers are the workers: JVM processes that execute your operators and hold your state in memory or on local disk. Each TaskManager offers a fixed number of task slots, which are the unit of scheduling: a job with parallelism 4 needs 4 slots to run. Slots partition a TaskManager's memory but not its CPU; think of them as reserved seats, not reserved cores.

Your code becomes a graph. When you submit a job, Flink turns your SQL or program into a job graph of operators (source → filter → aggregate → sink), then expands it into an execution graph where each operator is replicated across parallel subtasks. The Web UI shows you this graph live, with throughput and backpressure per operator. Learning to read it is a core skill and we start immediately.

There are three API layers, and you'll use two. Flink SQL and the Table API are declarative and optimised for you, and cover most real pipelines. The DataStream API gives you per-event control. Beneath that, ProcessFunction exposes the raw primitives: events, state, timers. The professional pattern is: SQL by default, drop down only when you must. Flink 2.x cleaned house here: the old DataSet batch API and the Scala API are gone, so everything you learn in this course is the current, long-term surface.

For the Snowflake brain: in Snowflake, compute wakes up, scans micro-partitions, produces a result, and goes back to sleep. A Flink job is the opposite: a long-lived program that holds state and reacts to every event as it arrives. Think "a query that never finishes", not "a query that runs fast". There is no equivalent of a warehouse auto-suspending; if the job stops, that is an incident.

Lab 0.1 · stand up the cluster

STEP 1Create the project and the compose file

Everything in this course lives in one directory. The compose file below defines a session cluster: a long-running JobManager and TaskManager that sit idle waiting for you to submit jobs, which is exactly what you want for a learning lab because you submit many small jobs to the same cluster.

mkdir -p ~/flink-lab/{flink-data,jobs,lib,scripts}
cd ~/flink-lab

The subdirectories: flink-data will hold checkpoints, savepoints and file sinks (shared with the containers so you can inspect them from your host), jobs holds code you submit, lib holds connector jars you download later, scripts holds Python data generators.

~/flink-lab/docker-compose.yml 
services:
  jobmanager:
    image: flink:2.3.0-java17
    ports:
      - "8081:8081"                # the Web UI, exposed to your laptop
    command: jobmanager            # same image, role chosen by command
    environment:
      - |
        FLINK_PROPERTIES=
        jobmanager.rpc.address: jobmanager
        state.checkpoints.dir: file:///flink-data/checkpoints
        state.savepoints.dir: file:///flink-data/savepoints
    volumes:
      - ./flink-data:/flink-data
      - ./jobs:/opt/flink/usrlib
      - ./lib:/opt/flink/extra-lib

  taskmanager:
    image: flink:2.3.0-java17
    depends_on: [jobmanager]
    command: taskmanager
    environment:
      - |
        FLINK_PROPERTIES=
        jobmanager.rpc.address: jobmanager
        taskmanager.numberOfTaskSlots: 4
    volumes:
      - ./flink-data:/flink-data
      - ./jobs:/opt/flink/usrlib
      - ./lib:/opt/flink/extra-lib

What each piece does: FLINK_PROPERTIES is the official image's way of injecting lines into Flink's config file at startup. jobmanager.rpc.address tells every process where the coordinator lives (Docker's DNS resolves the service name jobmanager). The two state.*.dir settings point durability at the shared volume, so recovery data survives container restarts and is visible on your host. taskmanager.numberOfTaskSlots: 4 means this one worker can run jobs up to parallelism 4. If the image tag has rolled forward by the time you read this, check Docker Hub for the current flink:2.x tag; nothing else changes.

STEP 2Start it and verify

docker compose up -d
docker compose ps

up -d pulls the image on first run and starts both containers detached. ps should show both services as running. Now open http://localhost:8081. You're looking at the JobManager's Web UI. Confirm three things: the overview shows Task Managers: 1 and Total Task Slots: 4; the Task Managers tab lists your worker with its memory breakdown; the Job Manager → Configuration tab shows the properties you injected. If a container is not running, read its logs:

docker compose logs jobmanager --tail 50

STEP 3Submit your first job

The image ships example jars. Submit the streaming WordCount from inside the JobManager container:

docker compose exec jobmanager ./bin/flink run examples/streaming/WordCount.jar

Unpacking that: docker compose exec jobmanager runs a command inside the JobManager container. ./bin/flink run is the Flink CLI's submit command: it uploads the jar to the cluster, the JobManager turns the program into a job graph, schedules its subtasks into free slots, runs it, and (because this example is bounded) the job finishes.

expected output (approximately) 
Job has been submitted with JobID 8f2e1c…
Program execution finished
Job with JobID 8f2e1c… has finished.

The job printed its word counts to the TaskManager's stdout, not yours: the CLI submits, the workers execute. This distinction matters forever, so prove it to yourself:

docker compose logs taskmanager | grep -m 5 "("
expected output 
(to,1)
(be,1)
(or,1)
(not,1)
(to,2)

Note (to,2): the count for "to" was updated as the second occurrence streamed in. You just watched incremental, stateful computation, which is the whole point of Flink. In the Web UI, open Completed Jobs → this job, and click through the graph: a source, a tokenizer, a keyed aggregation, a sink. Click an operator and look at records sent/received.

STEP 4Scale the workers

docker compose up -d --scale taskmanager=2

Compose starts a second identical TaskManager, which registers itself with the JobManager. Refresh the UI: 2 Task Managers, 8 slots. This is horizontal scaling in miniature, and it's exactly what an autoscaler does in production, just with more ceremony. Scale back down afterwards if you like (--scale taskmanager=1); the course assumes at least one.

STEP 5The first chaos drill

Start a job that never ends so there's something to break. The image ships a long-running example; StateMachineExample generates its own events and runs forever:

docker compose exec -d jobmanager ./bin/flink run \
  examples/streaming/StateMachineExample.jar

(-d on docker compose exec detaches so your terminal returns; the job keeps running, verify in the UI that it's RUNNING.) Now find a TaskManager container's name and kill it ungracefully:

docker ps --format '{{.Names}}' | grep taskmanager
docker kill flink-lab-taskmanager-1

docker kill sends SIGKILL: no graceful shutdown, the JVM just vanishes, like a spot instance reclaim. Watch the UI: the job flips to RESTARTING, and its exceptions tab shows a heartbeat timeout. Bring the worker back:

docker compose up -d

The job returns to RUNNING. Here's the uncomfortable truth to sit with: it restarted, but with no checkpointing configured, it lost all its state and restarted from scratch. Recovery ran, correctness didn't. Module 4 is where we fix that, and this drill is repeated there so you can see the difference. Cancel the job when done (UI → job → Cancel, or ./bin/flink cancel <jobId>).

STEP 6Install PyFlink on the host

Later modules run PyFlink scripts directly on your laptop (they spin up an in-process mini-cluster, no Docker needed, great for iteration). PyFlink needs a local Java 11 or 17:

java -version                      # need 11 or 17; on macOS: brew install openjdk@17
python3 -m venv ~/flink-lab/.venv
source ~/flink-lab/.venv/bin/activate
pip install "apache-flink==2.3.0"

Smoke test it. This runs a two-element pipeline entirely inside your Python process:

python3 -c "
from pyflink.datastream import StreamExecutionEnvironment
env = StreamExecutionEnvironment.get_execution_environment()
env.from_collection(['hello','flink']).print()
env.execute('smoke')"
expected output 
hello
flink
self-test (answers included, but think first)
  1. A job needs parallelism 6 and you have 4 slots. What happens, and what are your two fixes? The job can't acquire enough slots and fails to schedule (after a timeout). Fix by adding slots (more TaskManagers or more slots per TaskManager) or lowering the job's parallelism.
  2. Why did WordCount's output appear in the TaskManager logs rather than in your terminal? The CLI only submits; execution happens in TaskManager JVMs, so their stdout receives the print sink. The terminal only sees submission-side messages.
  3. What exactly did the chaos drill lose, and why? All operator state (the state machine's per-key progress), because no checkpoint existed to restore from. Restart policy controls whether a job resumes; checkpoints control what it resumes with.

Module 1 · week 2

Flink SQL first

You already think in SQL, so we start where your instincts transfer, then carefully break the one instinct that doesn't: that a table is data. In Flink, a table is a view over a changelog, and once you can read changelogs, most of Flink SQL becomes obvious.

The ideas

CREATE TABLE stores nothing. A Flink table definition is a schema plus connection config bound to an external system by the WITH (...) clause. It's closer to a Snowflake external table plus a Snowpipe than to a real table: the connector named in WITH decides where rows come from or go to, and the format decides how bytes become rows. Flink itself keeps only metadata (in an in-memory catalog by default, which is why your tables vanish when you close the SQL client, and why persistent catalogs exist).

Every table is secretly a changelog. Flink models all tables as streams of change rows, each tagged with a RowKind:

kindmeaningemitted by, for example
+Iinsert: a new rowany source; simple SELECT/WHERE results
-Uupdate-before: retract the old version of a rowa GROUP BY whose aggregate just changed
+Uupdate-after: here is the new versionsame GROUP BY, immediately after the -U
-Ddelete: the row is goneCDC sources, retractions in joins

Work one example by hand, because this is the load-bearing idea of the whole module. Query: SELECT customer, SUM(amount) FROM orders GROUP BY customer. Order (kai, 10) arrives → the result emits +I (kai, 10). Order (kai, 5) arrives → the old total is now wrong, so the result emits -U (kai, 10) then +U (kai, 15). A "continuous query" is just this: a standing computation that emits corrections forever. Queries that only ever emit +I produce an append-only stream (filters, projections, window aggregates after the window closes); queries that revise history produce an updating stream (plain GROUP BY, TOP-N, most joins). Which one you have determines which sinks you're allowed to use, and half of all beginner Flink SQL errors are "your sink can't accept updates".

For the Snowflake brain: a streaming GROUP BY behaves like a materialized view that updates on every input row, and its changelog is what a Snowflake stream object would show you: the deltas. When the SQL client later shows you changelog mode, you're looking at the same +I/-U/+U shapes a Snowflake stream calls METADATA$ACTION.

Lab 1.1 · the SQL client and your first continuous query

STEP 1Open the SQL client

docker compose exec -it jobmanager ./bin/sql-client.sh

This starts an interactive shell (you'll see a squirrel) that plans your SQL and submits each query as a job to the session cluster; the client itself does no processing. First, make results render inline in a readable grid:

SET 'sql-client.execution.result-mode' = 'tableau';

Three modes exist: table (a live-updating materialized grid), changelog (the raw +I/-U/+U rows scrolling past), and tableau (batch-style printing). You'll deliberately switch between them in step 3 because each reveals a different truth about the same query.

STEP 2Create a fake-data source

The datagen connector manufactures rows at a rate you choose, which makes it the perfect zero-dependency teaching source. Paste this whole statement:

CREATE TABLE orders (
  order_id    STRING,
  customer_id INT,
  amount      DECIMAL(10,2),
  order_time  AS localtimestamp,
  WATERMARK FOR order_time AS order_time - INTERVAL '5' SECOND
) WITH (
  'connector' = 'datagen',
  'rows-per-second' = '5',
  'fields.order_id.kind' = 'random',
  'fields.order_id.length' = '8',
  'fields.customer_id.min' = '1',
  'fields.customer_id.max' = '5',
  'fields.amount.min' = '1.00',
  'fields.amount.max' = '500.00'
);

Line by line: order_time AS localtimestamp is a computed column: not generated data but an expression evaluated per row, here stamping arrival time. The WATERMARK line declares event time for this table (Module 2 is entirely about what this means; for now it's future-proofing). In WITH: 5 rows/second keeps output humanly readable; the fields.* options control generation per column, and pinning customer_id to 1–5 guarantees repeated keys so aggregations visibly update. Now watch raw rows flow:

SELECT * FROM orders;

Rows scroll forever: your first unbounded query. Press Q to stop it. Stopping the display also cancels the underlying job; check Completed Jobs in the Web UI and you'll find it listed as CANCELED.

STEP 3Watch a continuous aggregation correct itself

SET 'sql-client.execution.result-mode' = 'changelog';

SELECT customer_id, COUNT(*) AS orders, SUM(amount) AS revenue
FROM orders
GROUP BY customer_id;
expected output (shape, not exact values) 
 op | customer_id | orders | revenue
 +I |           3 |      1 |   87.20
 +I |           1 |      1 |  240.10
 -U |           3 |      1 |   87.20
 +U |           3 |      2 |  301.75
 -U |           1 |      1 |  240.10
 +U |           1 |      2 |  350.60 …

Read the op column against the table in "The ideas": every new order for a customer retracts the old total and asserts the new one. This -U/+U pair is what any downstream consumer of this query must be able to absorb. Now see the friendly view of the same thing:

SET 'sql-client.execution.result-mode' = 'table';

SELECT customer_id, COUNT(*) AS orders, SUM(amount) AS revenue
FROM orders
GROUP BY customer_id;

Five rows, updating in place. Same query, same changelog underneath; the client is just applying the changelog for you, which is exactly what an upsert sink will do in Module 5. Quit with Q.

STEP 4Sink to files, and meet your first "sink can't accept updates" error

Try to write the updating aggregate to the filesystem connector:

CREATE TABLE revenue_files (
  customer_id INT, revenue DECIMAL(10,2)
) WITH (
  'connector' = 'filesystem',
  'path' = 'file:///flink-data/out/revenue',
  'format' = 'json'
);

INSERT INTO revenue_files
SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;
expected output 
[ERROR] … Table sink 'revenue_files' doesn't support consuming update changes
which is produced by node GroupAggregate…

Perfect: this error is the changelog theory becoming real. Files are append-only media; a -U row has nowhere to go. Two standard escapes exist: use an upsert-capable sink (Module 5), or reshape the query so it's append-only. Do the second now by wrapping amounts in a window later (Module 2) or, simplest today, sinking the raw append-only stream instead:

SET 'execution.checkpointing.interval' = '10s';

CREATE TABLE orders_files (
  order_id STRING, customer_id INT, amount DECIMAL(10,2)
) WITH (
  'connector' = 'filesystem',
  'path' = 'file:///flink-data/out/orders',
  'format' = 'json'
);

INSERT INTO orders_files SELECT order_id, customer_id, amount FROM orders;

The checkpoint SET line matters and is a classic gotcha: the filesystem sink writes to hidden in-progress part files and only finalises them when a checkpoint completes, because checkpoints are Flink's unit of "this output is now committed". No checkpointing, no visible files, forever. Let it run ~30 seconds, then on your host:

ls ~/flink-lab/flink-data/out/orders/
head -3 ~/flink-lab/flink-data/out/orders/part-*
expected output 
part-6f0a…-0-0
{"order_id":"a81xk2mQ","customer_id":4,"amount":331.42}
{"order_id":"Zz09qLpR","customer_id":1,"amount":12.05} …

Cancel the INSERT job in the Web UI when you're satisfied (INSERT statements run as detached jobs; the client prompt returned immediately after submitting it).

STEP 5TOP-N and EXPLAIN

A ranking query shows how violently an updating result can churn. This is Flink's canonical TOP-N pattern: rank in a subquery, filter on the rank outside:

SET 'sql-client.execution.result-mode' = 'changelog';

SELECT * FROM (
  SELECT customer_id, revenue,
         ROW_NUMBER() OVER (ORDER BY revenue DESC) AS rn
  FROM (SELECT customer_id, SUM(amount) AS revenue
        FROM orders GROUP BY customer_id)
) WHERE rn <= 3;

Watch the churn: every time totals reorder, rows are deleted and re-inserted with new ranks. Every one of those changes costs state and downstream work; when a TOP-N feels expensive in production, this is why. Finally, ask the planner what it actually built:

EXPLAIN
SELECT customer_id, SUM(amount) FROM orders GROUP BY customer_id;

You'll get three sections: the logical plan (your SQL, algebra-fied), the optimized physical plan, and notes on changelog modes per operator. Find GroupAggregate in the physical plan, then run the query and match the operator names against the boxes in the Web UI job graph. SQL → plan → running graph is one unbroken chain, and being able to walk it is the debugging skill.

self-test (answers included, but think first)
  1. Which of these produce an append-only stream: (a) WHERE filter, (b) GROUP BY, (c) window aggregate emitting once per closed window, (d) TOP-N? (a) and (c). Filters never revise emitted rows; closed windows emit final results once. GROUP BY and TOP-N continuously revise, so they're updating.
  2. Why did the filesystem sink produce no files until checkpointing was on? The sink stages writes in in-progress files and commits (renames) them only on checkpoint completion, so results are atomic with Flink's recovery point. No checkpoints means nothing is ever committed.
  3. Where did your orders table definition go when you closed the SQL client? Gone. The default catalog is in-memory and per-session. Persistent catalogs (or re-running DDL scripts via -i init files) fix this; the course keeps a growing init.sql from Module 5 onward.

Module 2 · week 3

Time, watermarks & windows

This is the module that separates people who use Flink from people who understand it. Your batch background gives you no intuition for watermarks, so this week is deliberately experimental: you'll control every event's timestamp by hand and break windows on purpose.

The ideas

Two clocks. Processing time is the wall clock of the machine handling the event. Event time is the timestamp inside the event, when the thing actually happened. They diverge because networks are slow, producers buffer, devices go offline, backfills happen. The business almost always means event time ("revenue between 12:00 and 12:01" means when orders were placed, not when your pipeline got around to them), so event time is the default professional choice, and it creates the problem this module exists to solve: events arrive out of order, so how do you ever know an event-time window is complete?

Watermarks are the answer, and they're just a claim. A watermark with value T is a statement flowing through the stream: "I believe no event with timestamp ≤ T is still coming." With the standard bounded-out-of-orderness strategy, the source continuously emits watermark = (max event timestamp seen so far) − (a bound you choose). Declare a 10-second bound and after seeing an event at 12:00:30, the watermark stands at 12:00:20, meaning anything claiming to have happened before 12:00:20 is now considered too late.

Windows fire when the watermark passes their end. A tumbling window [12:00:00, 12:01:00) does not fire at 12:01 on anyone's wall clock. It fires when the watermark reaches 12:01:00, i.e. when the stream itself has declared that minute complete. Until then the window sits in state, absorbing out-of-order events into their correct minute. This is the mechanism that buys correctness under disorder, and its price is latency: a 10-second bound means every window fires at least 10 seconds "late" relative to the data.

Two consequences you must feel in your hands. First, late data: an event whose timestamp is behind the watermark belongs to a window that already fired; in SQL it is silently dropped (count it with metrics in production). Second, watermarks merge on the minimum: an operator reading several parallel inputs takes the slowest input's watermark, so one stalled partition freezes every window downstream. That's the idle-source problem, and you'll cause it deliberately in the lab.

For the Kimball brain: a watermark answers the question your nightly batch never had to ask explicitly: "when is the data complete enough to publish?" Batch answers with the clock ("run at 2am, assume yesterday has landed"). Flink answers per-event and continuously, and makes you choose the completeness-vs-latency trade-off as a number.

Lab 2.1 · a source you fully control

STEP 1Write the event generator

The trick to actually seeing watermarks is a source where you decide every timestamp. This script appends JSON lines to a directory Flink will monitor; it emits clicks whose timestamps are mostly current, sometimes a bit old (out of order), and occasionally very old (properly late):

~/flink-lab/scripts/clickgen.py 
import json, random, time, os
from datetime import datetime, timedelta, timezone

OUT = os.path.expanduser("~/flink-lab/flink-data/events")
os.makedirs(OUT, exist_ok=True)
users = ["ana", "bo", "cai", "dee"]

def emit(f, ts, user):
    f.write(json.dumps({
        "user_id": user,
        "url": "/page/" + str(random.randint(1, 9)),
        "ts": ts.strftime("%Y-%m-%d %H:%M:%S.000")
    }) + "\n")
    f.flush()

with open(f"{OUT}/clicks.jsonl", "a") as f:
    while True:
        now = datetime.now(timezone.utc)
        r = random.random()
        if r < 0.80:   ts = now                                  # on time
        elif r < 0.97: ts = now - timedelta(seconds=random.randint(1, 8))   # out of order, inside bound
        else:          ts = now - timedelta(minutes=5)           # properly late
        emit(f, ts, random.choice(users))
        time.sleep(0.5)

Why these numbers: the watermark bound you'll declare is 10 seconds, so the 1–8 second stragglers land inside the bound (they'll be placed correctly) while the 5-minute stragglers land far behind the watermark (they'll be dropped). You've built a controlled experiment. Run it in its own terminal and leave it running:

source ~/flink-lab/.venv/bin/activate && python3 ~/flink-lab/scripts/clickgen.py

STEP 2Define the source with a watermark

In the SQL client:

CREATE TABLE clicks (
  user_id STRING,
  url     STRING,
  ts      TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '10' SECOND
) WITH (
  'connector' = 'filesystem',
  'path' = 'file:///flink-data/events',
  'format' = 'json',
  'source.monitor-interval' = '2s'
);

The two lines that matter: the WATERMARK clause implements exactly the formula from the ideas section (max ts seen, minus 10 seconds) and simultaneously marks ts as this table's event-time attribute, which is what permits event-time windows over it. source.monitor-interval turns the filesystem connector into a streaming source that re-scans the directory every 2 seconds for appended data instead of reading once and finishing. Sanity-check with SELECT * FROM clicks; (tableau mode), then Q.

Lab 2.2 · windows, disorder, and loss

STEP 3Tumbling windows with the TUMBLE table function

Modern Flink SQL expresses windows as table-valued functions: TUMBLE(...) takes your table and logically adds window_start/window_end columns; grouping by them gives per-window aggregates.

SET 'sql-client.execution.result-mode' = 'changelog';

SELECT window_start, window_end, COUNT(*) AS clicks
FROM TABLE(
  TUMBLE(TABLE clicks, DESCRIPTOR(ts), INTERVAL '1' MINUTE))
GROUP BY window_start, window_end;
expected output (one row per minute, arriving ~70s after the minute starts) 
 op | window_start        | window_end          | clicks
 +I | 2026-08-29 03:14:00 | 2026-08-29 03:15:00 |    118
 +I | 2026-08-29 03:15:00 | 2026-08-29 03:16:00 |    121

Two observations to make deliberately. First, the op column shows only +I: a closed window emits once and never revises, so this is an append-only stream and could go straight to the filesystem sink that rejected you in Module 1. Second, time the arrival of each row: the 03:14 window appears roughly 10 seconds after 03:15:00 in the data, because it fires only when the watermark (max ts − 10s) crosses 03:15:00. You are watching the latency you purchased with your out-of-orderness bound.

STEP 4Prove correct placement, then prove loss

While the window query runs, add a hand-crafted event that's 30 seconds old but for a current, still-open minute? No: better, make the two cases crisp. In a third terminal, append one event 8 seconds old (inside the bound) and one 5 minutes old (way behind the watermark):

python3 - << 'PY'
import json, os
from datetime import datetime, timedelta, timezone
p = os.path.expanduser("~/flink-lab/flink-data/events/manual.jsonl")
now = datetime.now(timezone.utc)
rows = [("inbound", now - timedelta(seconds=8)),
        ("ghost",   now - timedelta(minutes=5))]
with open(p, "a") as f:
    for user, ts in rows:
        f.write(json.dumps({"user_id": user, "url": "/x",
          "ts": ts.strftime("%Y-%m-%d %H:%M:%S.000")}) + "\n")
PY

Now watch: user inbound's click is counted in the correct (still-open) minute even though it arrived out of order; that's the watermark bound doing its job, holding windows open just long enough. User ghost never appears anywhere: its window fired minutes ago, and Flink SQL silently drops rows behind the watermark. Silently is the operative word; in production you watch the source operator's numLateRecordsDropped metric, or widen the bound, or route lates separately in the DataStream API. Nothing tells you here. Sit with that.

STEP 5Session windows

Sessions are windows whose boundaries come from the data: a session closes after a gap of inactivity per key. This is the shape behind "user sessions" in every analytics stack, and it's a one-liner here:

SELECT user_id, window_start, window_end, COUNT(*) AS clicks
FROM TABLE(
  SESSION(TABLE clicks PARTITION BY user_id, DESCRIPTOR(ts), INTERVAL '30' SECOND))
GROUP BY user_id, window_start, window_end;

PARTITION BY user_id makes gaps per-user. With four users clicking every ~2 seconds, gaps over 30s are rare, so to see sessions close, stop the generator (Ctrl-C) for 45 seconds and restart it: every user's session closes (once the watermark advances past gap-end), and new sessions begin. Which leads directly into the trap in step 6.

STEP 6The idle-source stall

Stop the generator and leave it stopped, with the tumbling-window query from step 3 running. Wait two minutes. Notice what does not happen: the last partial window never fires, even though the wall clock has long passed its end. Why: watermarks only advance when events arrive (max ts seen never grows), so a quiet source freezes event time itself. In multi-partition sources this is worse: one idle Kafka partition holds back the merged (minimum) watermark for everyone. The standard mitigation is an idleness timeout, after which a quiet source stops being counted in the minimum:

SET 'table.exec.source.idle-timeout' = '15s';

Re-run the window query with the generator on, then stop the generator again: this time, after 15 seconds of silence the source is marked idle... but with a single source and no events at all, there's still no max-timestamp to advance, so the final window still waits. The lesson lands anyway: idleness handling unblocks other inputs; it can't invent time. Restart the generator and watch everything catch up at once, which is also worth seeing: a burst of windows firing as the watermark leaps forward.

self-test (answers included, but think first)

Module 3 · week 4

The DataStream API

Now drop below SQL. The DataStream API is where you handle events one at a time, and KeyedProcessFunction with timers is Flink's most honest primitive: windows, joins, and SQL operators are all built from it. You'll work in PyFlink so the edit-run loop stays fast.

The ideas

The programming model is a pipeline of transformations. You get a StreamExecutionEnvironment, attach sources, chain transformations (map, filter, flat_map, key_by, process), attach sinks, and call execute(). Nothing runs until execute(): everything before it only builds the job graph. This is lazy evaluation exactly like a dbt DAG or a Spark plan, and it explains many beginner confusions ("my print before execute showed nothing").

key_by is a physical statement, not a GROUP BY. key_by(f) hash-partitions the stream: all events with the same key are routed over the network to the same parallel subtask, forever after. That guarantee is what makes keyed state possible: because subtask 2 is the only place events for key "ana" ever go, subtask 2 can keep a little local variable about "ana" and it is guaranteed complete. Keyed state is not a shared cache or an external store; it is state sharded by exactly the same hash as the data.

KeyedProcessFunction = event + state + timers. For each event you get process_element(value, ctx) with access to (a) the current key's state and (b) a timer service where you can register callbacks for a future time; when a timer fires you get on_timer(timestamp, ctx) with the same key's state. Event-driven logic plus scheduled logic plus per-key memory: that trio expresses almost anything, including "alert if a user goes quiet for 30 seconds", which is this module's centrepiece and a pattern you will reuse for the rest of your Flink life (timeouts, sessionisation, TTL cleanup, delayed actions).

For the dbt brain: SQL/Table API is your dbt layer: declarative, optimisable, right for 80% of jobs. DataStream is writing a custom materialization: you accept responsibility for state, time and correctness in exchange for control. Learn it well precisely so you can recognise when you don't need it.

Lab 3.2 · the inactivity detector

STEP 3Build it

The spec: for each user, if no click arrives for 30 seconds, emit an alert. Read the code top to bottom before running; the comments carry the teaching. The core trick is that each new event cancels the previous deadline and sets a fresh one, so exactly one live timer exists per key.

~/flink-lab/jobs/inactivity.py 
import json
from pyflink.common import WatermarkStrategy, Duration, Types
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.datastream.functions import KeyedProcessFunction, RuntimeContext
from pyflink.datastream.state import ValueStateDescriptor
from pyflink.datastream.connectors.file_system import FileSource, StreamFormat

GAP_MS = 30_000

class InactivityDetector(KeyedProcessFunction):

    def open(self, ctx: RuntimeContext):
        # Runs once per subtask before any data. Declare the state we need:
        # one long per key, remembering which deadline is currently armed.
        self.deadline = ctx.get_state(
            ValueStateDescriptor("deadline", Types.LONG()))

    def process_element(self, value, ctx):
        # Called for every event; self.deadline is scoped to THIS event's key.
        old = self.deadline.value()
        if old is not None:
            # the user is alive: cancel the pending alarm
            ctx.timer_service().delete_processing_time_timer(old)
        new = ctx.timer_service().current_processing_time() + GAP_MS
        ctx.timer_service().register_processing_time_timer(new)
        self.deadline.update(new)

    def on_timer(self, timestamp, ctx):
        # A timer that was never cancelled fired: the user went quiet.
        yield f"ALERT: {ctx.get_current_key()} inactive for 30s"
        self.deadline.clear()   # tidy up so state doesn't leak

env = StreamExecutionEnvironment.get_execution_environment()
env.set_parallelism(1)

src = (FileSource
       .for_record_stream_format(StreamFormat.text_line_format(),
                                 "/Users/YOU/flink-lab/flink-data/events")
       .monitor_continuously(Duration.of_seconds(2)).build())

(env.from_source(src, WatermarkStrategy.no_watermarks(), "clicks")
    .map(lambda line: json.loads(line))
    .key_by(lambda e: e["user_id"])
    .process(InactivityDetector(), output_type=Types.STRING())
    .print())

env.execute("inactivity_detector")

Run it with the generator on: silence (the alarms keep getting cancelled). Now stop the generator and wait. Thirty seconds later:

expected output

ALERT: dee inactive for 30s
ALERT: bo inactive for 30s
ALERT: cai inactive for 30s

Restart the generator and the cycle re-arms. Notice what you did not write: no polling loop, no shared dictionary of last-seen times, no background thread. The timer service and keyed state carried all of it, and (once checkpointing enters in Module 4) both survive crashes, which your hand-rolled dictionary never would.

Module 4 · week 5

State & fault tolerance

Flink's real product isn't stream processing, it's correct stateful stream processing under failure. This week you configure checkpoints, break the cluster again, watch it recover with state intact this time, and perform your first savepoint-based upgrade: the two operational moves you'll do for the rest of your Flink career.

The ideas

Where state actually lives. Every stateful operator (your GROUP BY, your inactivity detector, every open window) keeps its state in a state backend local to the TaskManager: either on the JVM heap (HashMap backend, fast, bounded by memory) or in embedded RocksDB (on local disk, scales past memory, pays serialisation cost). Flink 2.x adds a third direction, disaggregated state (the ForSt backend), where state lives primarily in remote storage for huge/elastic jobs; know it exists, use the defaults here.

Checkpoints: a consistent photograph of a moving system. On a schedule you set, the JobManager injects barriers into every source. Barriers flow with the data; when a barrier reaches an operator, the operator snapshots its state and passes the barrier on. Because a barrier occupies a fixed position in the stream, the assembled snapshot is consistent: it represents every operator's state as of exactly the same point in the data, plus the source offsets at that point. On failure, Flink restores all state from the last completed checkpoint and rewinds sources to its offsets: replay from a consistent photograph. That mechanism is what "exactly-once state consistency" means: each event affects state exactly once, even across crashes. Note what it doesn't promise: side effects (rows already pushed to an external system) may replay; making end-to-end exactly-once needs a transactional sink, which is Module 5's finale.

Checkpoints vs savepoints. Same snapshot machinery, different ownership. Checkpoints are Flink's: automatic, frequent, deleted as new ones complete, format optimised for fast recovery. Savepoints are yours: manually triggered, kept until you delete them, self-contained and portable, the mechanism for deploys, rescaling, migrations and A/B forks. The slogan worth memorising: checkpoints are for crashes, savepoints are for changes.

For the Snowflake brain: Time Travel gives you the illusion that failure-correctness is someone else's problem, because storage is remote, versioned, transactional. In Flink the "table" lives inside your running job, so durability is a protocol you configure, not a property you inherit. A checkpoint is the closest thing to a consistent snapshot across every operator's private table at one logical moment.

STEP 3State TTL: the leak valve

Your counter keeps one row of state per user forever. Four users, who cares; with user ids in the millions (or order ids: unbounded), the job's state grows until it dies. Flink SQL's blunt-but-standard control is a state TTL, after which idle keys are eligible for cleanup:

SET 'table.exec.state.ttl' = '1 h';

(Applies to queries planned after it's set.) Understand the trade you're making: expire a user's state and their next click starts a fresh count of 1, i.e. TTL deliberately trades correctness at the margins for bounded state. For the counter that's fine; for a financial dedup it might not be. TTL is a business decision wearing a config option's clothes; treat every unbounded-key stateful query as owing you an answer to "what bounds this state?"

Module 5 · week 6

Kafka in, Kafka out

Kafka is Flink's native habitat, and this week your theoretical Kafka knowledge becomes muscle memory. You'll add a broker to the lab, stream JSON through Flink SQL, meet the upsert-kafka sink that finally accepts your updating queries, and finish with end-to-end exactly-once, verified by trying to break it.

The ideas

Offsets: Flink trusts itself, not Kafka. The Kafka source records the partition offsets it has reached inside every checkpoint. On recovery it seeks to the checkpointed offsets, guaranteeing the rewind lines up exactly with the restored state. It also commits offsets to Kafka's consumer-group machinery, but only as a courtesy for monitoring tools; those commits are never the recovery source of truth. If you remember one Kafka-connector fact, make it this one.

Two sinks for two stream shapes. The plain kafka connector appends records to a topic: perfect for append-only results (raw events, closed windows). The upsert-kafka connector accepts updating streams by writing each change as a keyed record (latest value per key; deletes become tombstones) to a topic you should configure as compacted. A compacted topic whose latest-value-per-key is a table: exactly the state-topic pattern from your earlier Kafka reading, now produced by SQL.

End-to-end exactly-once = checkpoints + Kafka transactions. Module 4 established that replay can duplicate side effects. The Kafka sink closes the gap with two-phase commit: it writes output inside a Kafka transaction and commits that transaction only when the Flink checkpoint completes, so output becomes visible atomically with the recovery point. Consumers must opt in by reading read_committed, otherwise they see uncommitted (possibly doomed) rows. The cost is latency: output is only visible per checkpoint interval. Exactly-once is not a checkbox, it's a contract between checkpointing, the sink, and every consumer.

STEP 6End-to-end exactly-once, then attack it

Route the windowed (append-only) revenue to a plain Kafka sink under transactions:

SET 'execution.checkpointing.interval' = '10s';

CREATE TABLE minute_revenue (
  window_start TIMESTAMP(3), window_end TIMESTAMP(3),
  revenue DECIMAL(12,2)
) WITH (
  'connector' = 'kafka',
  'topic' = 'minute_revenue',
  'properties.bootstrap.servers' = 'kafka:29092',
  'format' = 'json',

  'sink.transactional-id-prefix' = 'lab-minute-rev'
);

sink.delivery-guarantee switches on the two-phase commit; the transactional-id prefix must be unique per sink (Kafka fences zombie producers by these ids after recovery, which is what makes replayed transactions safe). Consume it twice, once each way:

Now the attack: while both consumer and job run, docker kill a TaskManager, bring it back, let a few windows pass, and audit the read_committed output: every minute present exactly once, no gaps, no duplicates, despite a crash mid-stream. That audit is the whole point of the week.

self-test (answers included, but think first)
  1. After recovery, Kafka's consumer-group lag tool shows a weird jump for flink-lab. Why might it, and why is it not an incident? Group commits are a best-effort courtesy made on checkpoints; recovery seeks to checkpointed offsets regardless, so the group's committed position can lag or jump. The job's correctness never depended on it.
  2. What couples output visibility to checkpoint interval in exactly-once mode, and what's the tuning tension? Transactions commit on checkpoint completion, so consumers see data at checkpoint cadence. Shorter intervals cut latency but raise checkpoint overhead; longer intervals do the reverse.
  3. When is upsert-kafka the right sink and when is it a trap? Right when downstream wants current-state-per-key (a table view, cache feeding, CDC-style handoff). A trap when downstream needs full history/every change (compaction may collapse intermediate values) or when there's no meaningful primary key.

Module 6 · week 7

Joins, CDC & the table ecosystem

Real pipelines join streams against other streams and against slowly changing reference data, and increasingly they begin at a database's changelog. This week: the streaming join family ranked by what each costs, Flink CDC against a local Postgres, and the temporal join, which is your Kimball training's favourite Flink feature.

The ideas

Joins differ by how much of the past they must remember. In batch, a join scans two finite tables. In streaming, a row arriving now might match a row arriving next year, so the join type is really a policy about state:

joinsemanticsstate costreach for it when
regularstandard SQL join, both sides fully rememberedunbounded: both inputs kept forever (or until TTL)rarely as-is; usually a smell unless inputs are small/bounded
intervalmatch rows within an event-time window of each otherbounded: state expires as watermarks pass the intervaltwo event streams with a natural time affinity (order→payment within 15 min)
temporalenrich a stream with a versioned table as of the row's event timebounded-ish: versions retained until watermark says they're unreachablefacts × changing dimensions; correctness against history
lookupper-row query against an external system at processing timenone in Flink (optional cache)freshest-value enrichment, large dimensions, tolerable external load

CDC turns your OLTP database into a stream. A CDC source (Flink CDC, currently the 3.6 line, built on Debezium) does two phases: an initial consistent snapshot of the table, then a seamless switch to tailing the write-ahead log, emitting every subsequent INSERT/UPDATE/DELETE as +I / -U/+U / -D rows. Which is to say: a CDC table is a natively updating table, and everything you learned about changelogs applies with no new theory. Downstream aggregates consume the -U/+U pairs to stay correct as source rows change.

For the Kimball brain: a temporal join against a versioned table is a Type 2 SCD lookup performed continuously: "join each fact to the dimension version that was current at the fact's event time." The versioned table is the SCD2 dimension, maintained for you by CDC; the FOR SYSTEM_TIME AS OF clause is your effective-date BETWEEN join, evaluated per event, forever. Once that clicks, temporal joins stop being exotic and start being obviously necessary.

Lab 6.1 · joins between streams

STEP 1Feel the unbounded join, then bound it

Create a payments topic and extend ordergen (or write a sibling script) to emit a payment for ~90% of orders after a 5–60 second delay, keyed by order_id, with fields order_id, paid_amount, pay_time (declare a Kafka table payments_k over it, watermarked on pay_time, mirroring orders_k). First the naive join:

SELECT o.order_id, o.amount, p.paid_amount
FROM orders_k o
JOIN payments_k p ON o.order_id = p.order_id;

It works, and it's a trap: run it for a few minutes, open the job's checkpoint tab, and watch checkpointed size climb linearly and forever, because both entire streams are being remembered (any future payment may match any past order, says plain SQL semantics). Now express what the business actually means, that payments arrive within 15 minutes:

SELECT o.order_id, o.amount, p.paid_amount
FROM orders_k o, payments_k p
WHERE o.order_id = p.order_id
  AND p.pay_time BETWEEN o.order_time AND o.order_time + INTERVAL '15' MINUTE;

Same results for well-behaved data, but the time predicate lets Flink expire state as watermarks advance: re-check the checkpoint tab and watch size plateau. One WHERE clause is the difference between a pipeline and a slow-motion outage; the interval join is the professional default between two event streams.

Lab 6.2 · CDC and the temporal join

STEP 2Add Postgres with logical replication

docker-compose.yml (append under services:) 
  postgres:
    image: postgres:16
    ports: ["5432:5432"]
    command: postgres -c wal_level=logical
    environment:
      POSTGRES_USER: lab
      POSTGRES_PASSWORD: lab
      POSTGRES_DB: lab

wal_level=logical is the whole trick: it makes Postgres write enough detail into its WAL for external decoders to reconstruct row-level changes, which is what CDC tails. Start it, then seed a dimension:

docker compose up -d
docker compose exec -it postgres psql -U lab -d lab -c "
CREATE TABLE customers (
  customer_id TEXT PRIMARY KEY,
  segment     TEXT NOT NULL,
  updated_at  TIMESTAMP NOT NULL DEFAULT now());
INSERT INTO customers VALUES
  ('c1','smb',now()),('c2','smb',now()),('c3','mid',now()),
  ('c4','mid',now()),('c5','enterprise',now());"

Also download flink-sql-connector-postgres-cdc (the Flink CDC 3.6 line) into ~/flink-lab/lib/ and ADD JAR it, same routine as Kafka's connector.

STEP 3Watch a database become a stream

CREATE TABLE customers_cdc (
  customer_id STRING,
  segment     STRING,
  updated_at  TIMESTAMP(3),
  PRIMARY KEY (customer_id) NOT ENFORCED,
  WATERMARK FOR updated_at AS updated_at - INTERVAL '5' SECOND
) WITH (
  'connector' = 'postgres-cdc',
  'hostname' = 'postgres', 'port' = '5432',
  'username' = 'lab', 'password' = 'lab',
  'database-name' = 'lab', 'schema-name' = 'public',
  'table-name' = 'customers',
  'slot.name' = 'flink_lab',
  'decoding.plugin.name' = 'pgoutput'
);

The last two options: a replication slot is Postgres's bookmark guaranteeing WAL is retained until this consumer has read it (drop the slot if you delete this table for good, or WAL accumulates); pgoutput is Postgres's built-in logical decoder, so no server plugins to install. Now, in changelog mode:

SELECT * FROM customers_cdc;
expected output: snapshot phase, then live phase as you run updates in psql 
 op | customer_id | segment    | updated_at
 +I | c1          | smb        | 2026-08-29 06:41:02.113   ← snapshot rows
 +I | c2          | smb        | …
 -U | c3          | mid        | …                          ← after: UPDATE customers
 +U | c3          | enterprise | 2026-08-29 06:44:17.905      SET segment='enterprise',
                                                                  updated_at=now()
                                                                WHERE customer_id='c3';

Run that UPDATE in psql and watch the -U/+U pair arrive within a second or two. Module 1's changelog table, produced by a database this time. One idea, every source.

STEP 4The temporal join

customers_cdc qualifies as a versioned table: it has a primary key and a watermark, so Flink can maintain its versions over time. Enrich orders with the segment that was true when each order happened:

SELECT o.order_id, o.amount, c.segment
FROM orders_k o
LEFT JOIN customers_cdc FOR SYSTEM_TIME AS OF o.order_time AS c
  ON o.customer_id = c.customer_id;

Verify the "as of" is real with a controlled experiment: note the time, flip c2's segment in psql, and confirm that orders timestamped before your update still join to the old segment while later orders get the new one. Also notice enriched rows only emit as watermarks advance on both inputs: the join must be sure no older dimension version can still arrive before it commits to one. If the dimension goes quiet, output stalls: Module 2's minimum-watermark rule, now with a business consequence (this is why production versioned dims care about idleness settings).

STEP 5The lookup join, for contrast

Add the flink-connector-jdbc jar plus the Postgres JDBC driver to lib/, define a plain JDBC table over customers, add a processing-time column to orders (proc AS PROCTIME()), and join FOR SYSTEM_TIME AS OF o.proc. Each order triggers a keyed query against Postgres (cache options exist: lookup.cache.*). Contrast with step 4: the lookup join answers "what is the segment now?" with zero Flink state and per-row external load; the temporal join answers "what was it then?" from internally maintained versions. Neither is better; they answer different questions, and interviews love asking which you'd pick.

self-test (answers included, but think first)
  1. Why does a CDC source emit -U before +U, and what breaks downstream if the -U is dropped? The retraction tells stateful consumers to subtract the old version before adding the new. Drop it and any aggregate over the table double-counts: SUM(segment totals) would count c3 in both mid and enterprise.
  2. Your temporal join outputs nothing for the first minute after startup. Likeliest benign cause? Watermarks: the join waits until both sides' watermarks pass an order's time before emitting, and fresh sources need events to advance them (the dimension side especially, being low-traffic).
  3. Orders is high-volume; customers has 50M rows changing rarely, and you need enrichment as-of-now. Which join and why? Lookup join with caching: no Flink state for a huge dimension, as-of-now semantics wanted anyway, and rare changes make caching effective. Temporal would force Flink to hold versions of 50M keys.

Module 7 · week 8

Operations & the capstone

Finish by operating Flink the way you'd have to at work: read backpressure, rescale from a savepoint, and run one end-to-end pipeline that survives everything you throw at it. Nothing new is introduced here except operational judgment; the capstone is assembled entirely from parts you've already built.

The ideas

Backpressure is the system telling you where it hurts. Flink's network buffers are finite; when an operator can't keep up, buffers to it fill, and upstream operators slow down in a chain reaching back to the sources. The Web UI colours each operator by its busy/backpressured/idle percentages: read a backpressured graph from the sink end backwards, because the first non-backpressured, fully-busy operator downstream of the red ones is your bottleneck. Backpressure isn't an error, it's flow control working; sustained backpressure is a capacity problem wearing a UI colour.

Rescaling is a savepoint round trip. Parallelism isn't changed live: you stop with a savepoint and resume with a new parallelism, and Flink redistributes keyed state across the new subtasks. The hidden constant is max parallelism (default 128): keyed state is physically bucketed into that many key groups, which are the units reassigned during rescaling, so you can never scale beyond it without discarding state. Set it generously at job birth; it's the one setting you can't change later cheaply.

What to watch in production, translated to the four questions they answer: Is data flowing? (records in/out per operator, source idle time). Is it keeping up? (backpressure, busy ratios, Kafka records-lag-max). Is it healthy? (checkpoint duration/size trends, restart count). Is it fresh? (watermark lag = wall clock minus current watermark, the single best "how far behind is the business seeing reality" number). All of these export via Flink's metric reporters to your monitoring stack; sketching NRQL for watermark lag against a threshold is a worthwhile ten-minute exercise given your New Relic muscle.

The capstone: a sessionised revenue feed

Assemble one pipeline from parts you've already built, then operate it through four drills. Target architecture:

ordergen.py ──▶ kafka:orders ─────────────┐
                                          ├─▶ Flink SQL job:
psql updates ─▶ postgres ─▶ CDC:customers ┘    temporal join (M6)
                                               + 30-min session windows
                                                 per customer (M2)
                                               + revenue per segment/session
                                          ──▶ upsert-kafka:segment_revenue (M5)
                                               exactly-once, checkpointed (M4/M5)

Build guidance rather than a spec dump: put every DDL in init.sql so the whole pipeline reproduces from one client launch; sessionise with the SESSION window TVF partitioned by customer; join before windowing so revenue lands in the segment that was true at order time; sink with a PRIMARY KEY of (segment, window_start). Aim for boringly green before you start breaking it.

DRILL 1Stability

Run for 30 minutes. Pass criteria: zero restarts, checkpoint duration stable and under a few seconds, checkpointed size plateaued (if it climbs, find the unbounded state you've smuggled in; the usual suspect is a join without time bounds). Record your baseline numbers; drills are only meaningful against a baseline.

DRILL 2Failure

docker kill a TaskManager mid-flow, restore it, then audit the read_committed output for the affected windows: every (segment, session) present exactly once. You've done each half before; the point is proving the guarantees compose across a five-stage pipeline.

DRILL 3Upgrade

Business change request: session gap from 30 to 20 minutes. Stop with savepoint, edit the query, restore via execution.state-recovery.path, verify in-flight sessions carried across. Then write two sentences on which query changes this procedure could not absorb (structural changes that orphan operator state) because knowing the limits of your deploy mechanism is part of owning it.

DRILL 4Load

Drop ordergen's sleep to 10x the rate. Find the red operator in the backpressure view, walk backwards to the bottleneck, then fix it properly: stop with savepoint, resume with higher parallelism (SET 'parallelism.default' = '4'; before re-running the INSERT), confirm the graph goes green and Kafka lag drains. You have now done, end to end and on a laptop, the fundamental production manoeuvre of stream operations.

DRILL 5The runbook

Write one page as if handing this pipeline to your on-call rotation: what it does in two sentences, the four dashboards/metrics to check first, the three most likely failures with their signatures and responses (source stall → watermark lag with zero throughput; state leak → checkpoint size trend; sink outage → checkpoint failures with backpressure from the sink), and the savepoint restart procedure verbatim. If you can't write the runbook, the drills aren't finished; if you can, you've extracted the course into an artifact you'll actually reuse.

final self-test (answers included, but think first)
  1. Narrate your capstone's exactly-once story, source offset to visible sink record, no hand-waving. Kafka offsets are captured in each checkpoint alongside all operator state (join versions, session windows) via aligned barriers; the sink writes into a Kafka transaction committed on checkpoint completion; consumers read committed only. On failure: restore state, seek checkpointed offsets, replay; uncommitted transactions from the dead attempt are aborted and fenced by transactional id, so replayed output replaces rather than duplicates.
  2. You get one pageable metric. Which and why? Watermark lag on the final operator: it composes almost every failure (stalled source, backpressure, restart loops, stuck dimension) into the one number the business feels: how stale is the output. Checkpoint failure count is the defensible runner-up.
  3. At 100x, what breaks first in this design and what changes? Likely the single-node externals (Kafka, Postgres WAL/slot throughput) before Flink; within Flink, per-customer session state and the versioned join state force RocksDB/disaggregated state, higher max-parallelism set up front, and the JDBC lookup pattern (if used) needs caching or a different dimension strategy.

The stream never ends, but the course does.
