Module 0 · week 1

Orientation & the local lab

Get the mental model right, then get a real Flink cluster running on your laptop. By the end you'll have a JobManager, a TaskManager, the Web UI, and your first running job, and you'll have killed a TaskManager on purpose to see what happens.

Concepts to internalise

For the Snowflake brain: in Snowflake, compute wakes up, scans micro-partitions, produces a result, and goes to sleep. A Flink job is the opposite: a long-lived program that holds state in memory and reacts to every event as it arrives. Think "a query that never finishes" rather than "a query that runs fast".

Set up the lab

Create a project directory (this plan assumes ~/flink-lab) with this docker-compose.yml. It gives you a session cluster you'll reuse for most modules:

# ~/flink-lab/docker-compose.yml
services:
  jobmanager:
    image: flink:2.3.0-java17
    ports:
      - "8081:8081"
    command: jobmanager
    environment:
      - |
        FLINK_PROPERTIES=
        jobmanager.rpc.address: jobmanager
        state.checkpoints.dir: file:///flink-data/checkpoints
        state.savepoints.dir: file:///flink-data/savepoints
    volumes:
      - ./flink-data:/flink-data
      - ./jobs:/opt/flink/usrlib

  taskmanager:
    image: flink:2.3.0-java17
    depends_on: [jobmanager]
    command: taskmanager
    scale: 1
    environment:
      - |
        FLINK_PROPERTIES=
        jobmanager.rpc.address: jobmanager
        taskmanager.numberOfTaskSlots: 4
    volumes:
      - ./flink-data:/flink-data
      - ./jobs:/opt/flink/usrlib

Also install PyFlink on the host for later modules (needs Java 11 or 17 locally): pip install "apache-flink==2.3.0". If the exact image tag has moved on, check the tags on Docker Hub for flink and pick the current 2.x tag.

Reading

self-test: 3 questions before you move on
  1. A job needs parallelism 6 and you have 4 slots. What happens, and what are your two ways to fix it?
  2. What is the difference between the job graph you see in the UI and the code you wrote?
  3. Where does a slot live, and what does it actually reserve?

Module 1 · week 2

Flink SQL first

You already think in SQL, so start where your instincts transfer. The key mental shift is from tables-as-data to tables-as-changelogs: every Flink table is a view over a stream of inserts, updates, and deletes.

Concepts to internalise

For the Snowflake brain: CREATE TABLE in Flink stores no data. It's closer to an external table definition plus a Snowpipe: a schema and connection config over something that lives elsewhere. And a streaming SELECT COUNT(*) ... GROUP BY never returns; it emits a correction every time an input row arrives, like a materialized view that updates continuously.

Exercises

Open the SQL Client inside the running cluster:

docker compose exec jobmanager ./bin/sql-client.sh
self-test: 3 questions before you move on
  1. Which query shapes produce an append-only stream, and which force an updating stream?
  2. Why can't you write an updating result to a plain filesystem sink without windows or upsert support?
  3. What does the datagen connector's checkpoint behaviour imply about replayability?

Module 2 · week 3

Time, watermarks & windows

This is the module that separates people who use Flink from people who understand it. Event time, watermarks, and lateness are the ideas your batch background gives you no intuition for, so this week is deliberately experimental: you'll break windows on purpose.

Concepts to internalise

For the Kimball brain: a watermark is the streaming answer to the question your nightly batch never had to ask: "when is the day's data complete enough to publish?" Batch answers it with the clock ("run at 2am"). Flink answers it per-event and continuously, and lets you choose the trade-off between latency and completeness explicitly.

Exercises

Do these in the SQL Client. The trick to seeing watermarks clearly is a source you control, so first write a tiny Python generator that appends JSON lines with deliberately shuffled timestamps to a file under ./flink-data/events/, then define a filesystem source over it with a watermark:

CREATE TABLE clicks (
  user_id STRING,
  url STRING,
  ts TIMESTAMP(3),
  WATERMARK FOR ts AS ts - INTERVAL '10' SECOND
) WITH (
  'connector' = 'filesystem',
  'path' = 'file:///flink-data/events',
  'format' = 'json',
  'source.monitor-interval' = '5s'
);
self-test: 3 questions before you move on
  1. A window [12:00, 12:01) fires. Exactly what watermark condition made it fire?
  2. Two Kafka partitions, one fast and one slow: whose watermark wins downstream, and why?
  3. When would you pick a larger out-of-orderness bound, and what do you pay for it?

Module 3 · week 4

The DataStream API

Now drop below SQL. The DataStream API is where you control events one at a time, and ProcessFunction with timers is Flink's most honest primitive: everything else is built on it. You'll use PyFlink so the iteration loop stays fast on a laptop.

Concepts to internalise

For the dbt brain: SQL/Table API is your dbt layer: declarative, optimisable, 80% of jobs. DataStream is the escape hatch, like writing a custom materialization: you take responsibility for state, time, and correctness in exchange for full control. Learn it well precisely so you can recognise when you don't need it.

Exercises

Skeleton for a local PyFlink script (runs in-process, no cluster needed, which makes print-debugging pleasant):

from pyflink.datastream import StreamExecutionEnvironment

env = StreamExecutionEnvironment.get_execution_environment()
env.set_parallelism(1)

ds = env.from_collection([("lin", 1), ("kai", 2), ("lin", 3)])
ds.key_by(lambda e: e[0]) \
  .map(lambda e: (e[0], e[1] * 10)) \
  .print()

env.execute("hello_datastream")
self-test: 3 questions before you move on
  1. Why can keyed state only be used after keyBy, mechanically?
  2. Your map function keeps a Python dict as a "cache". What is wrong with that under failure and rescaling?
  3. What is the difference between a processing-time timer and an event-time timer firing?

Module 4 · week 5

State & fault tolerance

Flink's real product is not stream processing, it's correct stateful stream processing under failure. This week you make checkpoints, break things, recover, and take your first savepoint. All of it works on a laptop because the mechanisms are the same at any scale.

Concepts to internalise

For the Snowflake brain: Time Travel gives you the illusion that correctness under failure is someone else's problem, because storage is remote, versioned, and transactional. In Flink the state lives inside your job, so durability is a protocol you configure, not a property you inherit. A checkpoint is closest to a consistent snapshot across every operator's local "table" at a single logical point in the stream.

Exercises

Your compose file already points checkpoints and savepoints at /flink-data, so everything lands on your host disk where you can poke at it.

self-test: 3 questions before you move on
  1. Exactly-once checkpointing is on, yet your sink wrote duplicates. Name two legitimate reasons.
  2. Why are savepoints the upgrade mechanism while checkpoints are the recovery mechanism?
  3. What grows unboundedly in a keyed job with no TTL and an unbounded key space, and what are your options?

Module 5 · week 6

Kafka in, Kafka out

Kafka is Flink's native habitat, and it turns your theoretical Kafka knowledge into muscle memory. You'll add a single-node KRaft broker to the lab, stream JSON through Flink SQL, and finish with end-to-end exactly-once using Kafka transactions.

Extend the lab

Add to your compose file:

  kafka:
    image: apache/kafka:3.9.0
    ports:
      - "9092:9092"
    environment:
      KAFKA_NODE_ID: 1
      KAFKA_PROCESS_ROLES: broker,controller
      KAFKA_CONTROLLER_QUORUM_VOTERS: 1@kafka:29093
      KAFKA_LISTENERS: PLAINTEXT://:29092,CONTROLLER://:29093,EXTERNAL://:9092
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:29092,EXTERNAL://localhost:9092
      KAFKA_LISTENER_SECURITY_PROTOCOL_MAP: PLAINTEXT:PLAINTEXT,CONTROLLER:PLAINTEXT,EXTERNAL:PLAINTEXT
      KAFKA_CONTROLLER_LISTENER_NAMES: CONTROLLER
      KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR: 1

Then drop the Kafka SQL connector jar (grab flink-sql-connector-kafka for your Flink 2.x line from the downloads page) into /opt/flink/lib on both Flink containers, or mount it, and restart them.

Exercises

self-test: 3 questions before you move on
  1. Why does Flink commit Kafka offsets only as a courtesy, and what is the source of truth?
  2. What do Kafka transactions cost you in end-to-end latency, and what setting couples them to checkpoints?
  3. When is upsert-kafka the right sink and when is it a trap?

Module 6 · week 7

Joins, CDC & the table ecosystem

Real pipelines join streams against other streams and against slowly changing reference data, and increasingly they start from database changelogs. This week: the streaming join family, Flink CDC against a local Postgres, and a look at where results should land.

Concepts to internalise

For the Kimball brain: a temporal join against a versioned table is a Type 2 SCD lookup performed continuously: "join each fact to the dimension row that was current at the fact's event time." Once that clicks, temporal joins stop being exotic and start being obviously necessary.

Exercises

Add a postgres:16 service to the lab with wal_level=logical (set via command flag), create a customers table, and drop the Postgres CDC connector jar into the Flink containers.

self-test: 3 questions before you move on
  1. Rank the four join types by state footprint and explain each ranking.
  2. Why does a CDC source emit -U/+U pairs, and what must a downstream aggregate do with them?
  3. Your temporal join returns nulls for early events. What about watermarks explains this?

Module 7 · week 8

Operations & the capstone

Finish by operating Flink like you'd have to at work: read backpressure, reason about parallelism, and run one end-to-end pipeline that survives everything you throw at it. This capstone is deliberately shaped like a serving-layer feed you might one day build for real.

Concepts to internalise

Capstone: the sessionised revenue feed

Build one pipeline, end to end, on your laptop: Python generator → Kafka clickstream and orders topics → Flink job that (a) sessionises clicks per user with a 30-minute gap, (b) enriches orders with the customer's CDC-fed segment via temporal join, (c) emits per-segment revenue per session window → upsert-kafka segment_revenue, exactly-once, checkpointed. Then operate it:

final self-test
  1. Explain your capstone's exactly-once story from source offset to committed sink transaction, with no hand-waving.
  2. Which single metric would you page on first, and why that one?
  3. Where would this pipeline break first at 100x scale, and what would you change?
